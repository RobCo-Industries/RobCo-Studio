# Spike K1: our own QEMU 10.1.2 on three systems

## The question

Does QEMU 10.1.2, built by us on the GitHub Windows and macOS runners, pass RobCo-Core's canary tests?

## The method

- Workflow: `.github/workflows/spike-k1.yml`. Build script: `spikes/k1/build-qemu.sh`.
- Source: the official `qemu-10.1.2.tar.xz`, checked against the SHA-256 that RobCo-Core's `ci/Dockerfile` pins. QEMU publishes a GPG signature, not a SHA-256. The spike did not check the signature.
- Configure line, the same as RobCo-Core's CI container:

  ```
  ./configure --target-list=arm-softmmu,aarch64-softmmu --without-default-features
    --enable-fdt=system --enable-pixman --disable-docs --disable-tools
    --disable-guest-agent --disable-slirp --disable-werror
  ```

  macOS adds `--extra-cflags=-I/opt/homebrew/include --extra-ldflags=-L/opt/homebrew/lib`, because meson does not find Homebrew's libfdt otherwise.
- Only the two emulators are built, with `ninja qemu-system-arm qemu-system-aarch64`. A plain `make` also builds QEMU's unit tests, and one of them does not link with MinGW (`test-vmstate`, `qemu_ftruncate64`).
- Build hosts: Ubuntu with apt packages. macOS with Homebrew `glib pixman dtc`. Windows with MSYS2 UCRT64 `glib2 pixman dtc meson`, plus `diffutils` and `pycotap` from PyPI.
- Packing: binaries are stripped. On macOS `dylibbundler` copies the Homebrew libraries into `lib/` and rewrites them to `@executable_path/../lib`, then everything gets an ad hoc signature. On Windows the MSYS2 DLLs are copied next to the `.exe` files. Linux is not packed.
- Canary: RobCo-Core at commit `c8220b2`, `tests/canary/test_qemu_assumptions.py`, 78 cases, run on a fresh runner that has none of the build tools. The cross compiler is xPack `arm-none-eabi-gcc` 15.2.1-1.1, checked against its published SHA-256.
  - Linux and macOS: the suite as it is, with `pytest`.
  - Windows: the same test file with the plugin `spikes/k1/k1_tcp.py`. It swaps the harness's Unix sockets for TCP on 127.0.0.1, and its process group signals for terminate and kill. It also builds the firmware stub with gcc and objcopy, as the stub's Makefile does, since the runner has no `make`. No test body and no expectation changes.

## The result

Numbers come from two CI runs on GitHub hosted runners: run A is [45657416334](https://github.com/RobCo-Industries/RobCo-Studio/actions/runs/45657416334) with a rerun, run B is [45662886039](https://github.com/RobCo-Industries/RobCo-Studio/actions/runs/45662886039) with a rerun. Run B differs from run A only by a fix to the macOS packing. Sizes are `du -sk`.

| | Ubuntu (`ubuntu-latest`, x86-64) | macOS (`macos-latest`, arm64) | Windows (`windows-latest`, x86-64) |
|---|---|---|---|
| Build | succeeds | succeeds | succeeds |
| Configure and build time, run A then B | 219 s, 187 s, 4 jobs | 242 s, 184 s, 3 jobs | 641 s, 776 s, 4 jobs |
| Two binaries, not stripped | 195,720 KiB | 65,052 KiB | 208,340 KiB |
| Package, stripped, with libraries | 61,600 KiB, no libraries | 57,532 KiB | 58,672 KiB |
| Libraries outside the system | glib, pcre2, pixman, libfdt, zlib, libatomic | glib, pcre2, intl, pixman, libfdt | glib, pcre2, intl, iconv, pixman, libfdt, zlib, winpthread |
| Portable | no, needs the apt packages | yes on a fresh runner, see below | yes on a fresh runner |
| Canary, run A | 77 of 78, twice | not run: the package aborted, see below | 78 of 78, twice |
| Canary, run B | 78 of 78 | 77 of 78 | 77 of 78 |

In run A the macOS package did not start: `dylibbundler` wrote the run path `@executable_path/../lib/` twice and dyld aborts on a duplicate. Run B removes the duplicate, and the macOS canary ran.

The Windows and macOS canary jobs ran the packed build on a fresh runner with no MSYS2 or Homebrew libraries on the path. That is the portability evidence. The Linux job installed `libglib2.0-0t64 libpixman-1-0 libfdt1 zlib1g` first.

Every failure is the same case, `test_v23_spi0_byte_rate[raspi3b]`: `KeyError: 'R15'` at line 621 of the canary. It failed on Linux in run A, on Windows and macOS in run B, and passed on Linux in run B and on Windows in run A. The test reads `R15` from `info registers` right after boot. On `raspi3b` CPU0 may still run the AArch64 shim then, and QEMU prints `PC=` and no `R15`. This points to a race in the test, not to the build. The other 77 cases passed on every system in every run. Not proven: nobody has run that case many times in RobCo-Core's own container to see if it fails there too.

## What it means for Studio

- Our own build of QEMU 10.1.2 works on all three systems. Plan risk 1 does not need the container fallback for QEMU.
- Windows needs TCP. Python on Windows has no `AF_UNIX`, and the suite's harness uses Unix sockets and process groups. Studio's plan already uses TCP loopback for QMP, serial and qtest (section 4.4). The Windows canary run proves that QEMU on Windows serves all of these over TCP, with qtest as a client that connects to Studio.
- The QEMU recipe for Windows needs three changes from the Linux one: skip the `roms/` and `tests/lcitool/libvirt-ci` folders when unpacking, because their symlinks fail on Windows. Give `configure` `pycotap` and `diffutils`. Build the two emulator targets only.
- Packing is needed on macOS and Windows and was enough on a fresh runner. Each package carries LGPL libraries (glib, intl, iconv, pixman is MIT, libfdt is BSD or GPL-2.0). Their notices and sources belong in the release next to QEMU's source archive.

## What stays unknown

- Linux portability. Not tested. To make it portable: copy the six libraries into `lib/` and set the run path to `$ORIGIN/../lib` with `patchelf`, or link glib and pixman statically. glibc stays a system library, so the build host sets the oldest glibc the package runs on. Building in an older distribution or the manylinux image would widen that.
- macOS Intel. Not built. `macos-latest` is arm64. A universal or x86-64 build needs its own job.
- Oldest macOS and Windows versions the package runs on. Not tested. The macOS binaries target the runner's own system version unless `MACOSX_DEPLOYMENT_TARGET` is set.
- A user's machine without developer tools, Gatekeeper on a downloaded archive, and an antivirus scan on Windows. Not tested. A downloaded macOS binary with an ad hoc signature gets quarantined, so the SDK manager must clear the attribute or the release must be signed and notarised.
- The GPG signature of the QEMU archive. Not checked.
- Timing-sensitive cases on hosted runners over many runs. Each system ran the suite once or twice.
