# Spike K7: a plain text editor in egui

## The question

Does a plain text editor hold up in egui 0.37? The test file is C source of 5,000 lines. The editor needs line numbers that stay in step with the text, colours for C, typing, selection, copy and paste, undo and redo, search, go to line, open and save with the exact bytes, a dirty mark and a monospace font. It has no analysis and no completion.

The known risk: egui's `TextEdit` lays out the whole text again when it changes. This spike measures what that costs at 500, 5,000 and 20,000 lines.

## Method

- `spikes/k7/`: one Cargo workspace, one program, `eframe` 0.37.0 with its default features and `egui_kittest` 0.37.0 for tests. These are the versions K4 pinned. The lock file has the same 427 packages as K4's egui lock file: the editor adds no package.
- The editor is egui's own `TextEdit::multiline` with `code_editor()`, inside a `ScrollArea`, in `src/lib.rs`:
  - Colours come from a layouter. It runs our tokenizer, `src/c_lex.rs`, about 150 lines, over the whole text and builds one `LayoutJob`. The job is kept and reused while the text is unchanged.
  - The gutter is painted by us. It finds the first visible row of the text galley and paints one number at each visible row's own position. Lines do not wrap, so row i is line i + 1.
  - Search, previous and next, and go to line set a selection and scroll it into view. Copy, paste, undo, redo and tab are `TextEdit`'s own.
  - Open and save go through `src/file.rs`. The editor holds LF only. A file with CRLF on every line is read as LF and written back as CRLF. A file that is not UTF-8, or that mixes CRLF and LF, is refused with a message and the editor text is left alone. There is a path field, not a file dialog.
  - The dirty mark is a label, "modified" or "saved", from comparing the text with the text last opened or saved.
- Headless tests, `tests/headless.rs` and `tests/files.rs`, drive the editor through `egui_kittest` with no window. They find buttons through the accessibility tree.
- A benchmark mode, `src/main.rs`. `K7_BENCH=type-end|type-mid|scroll` and `K7_LINES=n` open a window on a generated C file of n lines. Typing sends one `x` text event per frame through `raw_input_hook`, at the end of the file or at the start of the middle line. Scrolling sets the scroll position to the next 40 lines before each frame is drawn. After 10 s it prints the frame rate, the process CPU use from `ps`, and the time spent in the editor's `ui` per frame, then exits.
- Each benchmark proves it did the thing, and exits non-zero if not:
  - typing: the number of frames in which the text length changed must not be zero. For `type-mid`, the middle line must start with the typed `xx`.
  - scrolling: the number of frames in which the gutter's first line changed must not be zero, and in every frame the gutter's first line must equal the text's first line. The text's first line is found apart from the gutter: the galley character at the top of the view, mapped to a line by counting newlines in the text.
- `tests/cost.rs`, ignored by default, splits the cost of one edit with no window. For 20 edits in the middle line it times the tokenizer and job over the whole text, egui's layout of that job, and the same two steps over 60 lines, which is what a view that lays out visible lines only would do.
- The CI job [`spike-k7.yml`](../../.github/workflows/spike-k7.yml) runs on the three hosted runners with no cache: format check, clean debug build, clippy with `-D warnings`, the headless tests, clean release build, release size, and the cost test.
- Window rates were measured on this Mac only: an Apple Silicon laptop with a 120 Hz display, release build, `-j 3`. Nine runs of about 10 s each, one per row below, each window closed by itself. The log of those runs was kept outside the repository and is quoted here.

The first run, type at the end with 5,000 lines, also printed 1,132 "gutter mismatch" frames. That count was wrong: the check that finds the text's first line is off while typing, so it compared against a stale value. The benchmark now counts mismatches only when that check is on, and the eight later runs used that build. No run was repeated.

Typing sends one character per frame, about 117 a second. That is far faster than a person types, so it is a worst case for the rate, not a typing session.

The worst frame is likely one of the first, when the whole file is laid out for the first time. That was not checked frame by frame.

Ubuntu and Windows: not run. Hosted runners have no display.

These are timings on shared hosted runners, one run each. They show the same shape on the three systems. They do not give a frame rate.

egui 0.37 does not lay out every glyph again on an edit. Its galley cache splits a job on newlines and caches each paragraph, so after an edit only the changed line is laid out. It still hashes the whole job, rebuilds the whole galley from the cached paragraphs, and our layouter tokenizes the whole text. On this Mac that is 0.9 ms at 5,000 lines and 3.4 ms at 20,000 lines, and it grows with the file.

The window's `ui` time is larger than these two steps: 3.9 ms against 1.4 ms at 5,000 lines, 16 ms against 5.4 ms at 20,000 lines. The rest was not broken down. From reading egui's code, likely parts are `TextEdit`'s undo state, which keeps a copy of the text, painting the whole galley, and the copy and compare of the whole text that the layouter cache and the dirty mark do each frame. This is a reading, not a measurement.

With no edit, scrolling still costs 1 ms at 5,000 lines and 3.3 ms at 20,000. Our layouter returns the cached job, but egui hashes it in full each frame. The scroll benchmark also adds its own check, which scans the text each frame.

Laying out only 60 visible lines costs about 0.02 ms at every size. That is the text part of a view that draws visible lines only. Such a view was not built: it also needs its own cursor, selection, input, undo and scrolling, which is the larger part of the work.

## What it means for Studio

The plain editor holds up in egui at 5,000 lines on this Mac: 113 to 117 fps while typing one character a frame at the end or in the middle, and 117 fps while scrolling, with the gutter in step in every frame. Every feature the brief lists works on egui's own `TextEdit` with a layouter and a painted gutter, with no new package. The headless tests cover all of them except mouse selection, the font and the colours on screen.

Approach to build on: `TextEdit` with our layouter and gutter, as here. Two egui behaviours cost time in this spike and will cost it again in S2:

- A selection set from code on a `TextEdit` without focus is collapsed by egui. Focus must be requested a frame before the selection is set.
- `TextEdit` holds a `String`. There is no rope and no line index, so line counts, go to line and search each scan the text.

What a plain editor will not do well in egui:

- Files much larger than 5,000 lines. Cost per edit grows with the whole file. At 20,000 lines typing fell to 57 to 60 fps and one core was busy.
- Line wrapping with a gutter. This gutter assumes one row per line. Wrapping was not tried.
- Anything that needs per-line state that outlives an edit: folding, markers in the gutter, a second view of the same text. `TextEdit` owns the cursor and the undo history.
- A dirty mark, line count and colours that do not scan the whole text each change. They would need our own buffer.

When to look at the D1 decision again, with these numbers:

- Files above about 10,000 lines must edit at the display rate. The rate stayed at the vsync limit at 5,000 lines and halved at 20,000. 10,000 lines was not measured.
- The editor grows towards analysis, completion, folding, several cursors or diagnostics in the gutter. Each needs a buffer and a view of our own, which is the visible-lines view this spike did not build.
- Options at that point, from this spike and the plan: write our own visible-lines view on egui, whose text layout costs about 0.02 ms a screen; try a crate such as `egui-pop-editors` or `egui_code_editor`; or weigh GPUI with GPUI Kit's editor, as section 4.2 of the plan says. This spike does not pick.

## What stays unknown

- Frame rates on Ubuntu and Windows: not run, hosted runners have no display.
- 10,000 lines: not measured. The point where the rate leaves the vsync limit lies between 5,000 and 20,000 lines on this Mac.
- A slower machine than this Mac: not run.
- Mouse selection, double-click and drag: not tested.
- The colours and the font on screen: not tested, no image snapshot.
- Real paste from the system clipboard and real copy to it: the tests check egui's copy command and a paste event, not the system clipboard.
- Undo grouping: the test undoes one typed run. How egui groups longer typing into undo steps was not checked.
- Files with a byte order mark, lone CR, or no final newline in CRLF mode: not tested. A lone CR is kept as text.
- The cost breakdown of the 2.5 ms per frame at 5,000 lines that is not tokenizing or layout.
- A visible-lines view and the two crates: not built, not tried.
