# Spike K4: egui or GPUI for the Studio window

## The question

The plan picks egui with eframe for Studio's window and names GPUI as the runner-up. This spike runs the same four tests on both, at pinned versions, on Ubuntu, macOS and Windows, so the pick is confirmed or reversed on evidence.

The four tests:

1. A 32 by 32 indexed sprite, enlarged with sharp pixels, a grid, zoom in and out, and a click that sets one pixel.
2. A 320 by 240 view fed a new frame 30 times a second, scaled by a whole factor with sharp pixels.
3. A log of 100,000 lines that scrolls and can jump to the end.
4. A headless test with no display: find a button, press it, check the state.

## Method

- `spikes/k4/egui/`: `eframe` 0.37.0 with its default features, which use wgpu, and `egui_kittest` 0.37.0.
- `spikes/k4/gpui/`: `gpui` 0.2.2, the only official release on crates.io, with the `runtime_shaders` feature. Its tests use `gpui`'s own `test-support` feature.
- Each is its own Cargo workspace with a committed lock file. Both build from crates.io only. No git dependency.
- Each program shows the three views on tabs. With `K4_BENCH=canvas|screen|log` set, it opens one tab, keeps it busy, and a timer prints frames per second, simulator frames per second and process CPU use after 10 seconds, then exits. The canvas view sets one pixel per frame at a fixed zoom: the benchmark does not zoom or click. The screen view makes a new frame on a 30 Hz schedule. In egui, the log view sets the scroll position before the log is drawn: each cycle of 200 frames steps down 500 rows per frame, jumps to the end, and goes back to the top. It counts how often the first visible row changed and how many frames showed the last line, and exits with an error if either is zero. The GPUI log view jumps between the first and the last line every frame; it was not checked again.
- How each toolkit keeps pixels sharp:
  - egui: textures with `TextureOptions::NEAREST`, drawn at any size.
  - GPUI: its three renderers sample every image with a linear filter, confirmed in `shaders.metal` of 0.2.2. The sprite is drawn as one quad per pixel. The screen is scaled on the CPU to device pixels before upload, so the GPU samples it 1:1. A new image is uploaded for each simulator frame and the old one dropped.
- The CI job [`spike-k4.yml`](../../.github/workflows/spike-k4.yml) builds both on the three hosted runners with no cache, runs the headless test, and records the times and sizes in the run summary.
- Rates and CPU use need a real window, so they were measured on this Mac only: an Apple Silicon laptop with a 120 Hz display, release builds.

### Why GPUI does not build on Ubuntu

`gpui` 0.2.2 needs `gpui_http_client`, which needs `zed-async-tar` with its default `xattr` feature, which pins `xattr` 0.2.3. That crate uses `libc::ENOATTR` on Linux. `libc` removed it in 0.2.190. Today's `mio`, needed through `tokio`, requires `libc` 0.2.190 or later. So a fresh resolve of `gpui` 0.2.2 fails to compile on Linux ([job log](https://github.com/RobCo-Industries/RobCo-Studio/actions/runs/45654286086/job/139346681293)). Getting past it means pinning older `libc`, `mio`, `tokio` and `tokio-util` by hand. The spike did not go further.

The CI job "gpui on ubuntu: known not to build" checks this finding. It passed in [run 45666339751](https://github.com/RobCo-Industries/RobCo-Studio/actions/runs/45666339751/job/139389371967). It passes only when the build fails with the `xattr` and `ENOATTR` error. If it turns red, either `gpui` now builds on Ubuntu and this page is out of date, or the build breaks for another reason, which the job log shows.

### Rates on this Mac

The display runs at 120 Hz, so 117 to 118 fps is the vsync limit. Each program ran several times for 10 seconds. The table gives the best run. Many runs were throttled to 10 to 90 fps for both toolkits, because macOS slows a window that is not in front, and the machine was in use. These numbers show that both reach the display rate. They do not rank the two on speed.

The first egui log number, 117.4 fps, was measured on a still log: the benchmark set a scroll delta after the log was drawn, and egui drops it at the start of the next frame. The benchmark now sets the scroll position before the log is drawn. One run on this Mac gave 88.2 fps and 12 % CPU over 10 seconds. In that run the first visible row changed 877 times in 882 frames, and 4 frames showed the last line. Whether the window was in front was not checked, so the rate may be throttled. It is a single run and does not show whether scrolling costs frames.

The GPUI log number was not checked again and may have the same fault.

GPUI's screen tab never reached a clean run. Its design costs more for this test: every simulator frame is scaled on the CPU to device pixels, here a 2560 by 1920 image, and uploaded as a new image, because GPUI has no nearest sampling.

## What it means for Studio

egui passes both headless tests in CI on all three systems. On this Mac it reaches the display rate in tests 1 and 2, and holds 88 fps in one scrolling log run. It builds in about half the time of GPUI and pulls 427 packages against 718. It does sharp pixels with one texture option.

GPUI's official release does not build on Linux today. On macOS and Windows it builds and its one headless test passes. That test presses two buttons. It does not scroll the log or press Jump to end. Sharp pixels need a workaround in our code: one quad per pixel for the editor, and CPU scaling for the screen. The screen workaround holds only at whole display scales. It uploads the image at `round(k * scale)` device pixels per simulator pixel, but draws it into bounds of `k * scale`. At 125 %, with k = 3, that is 4 against 3.75, and GPUI's linear filter blurs the image. It was looked at on this Mac's display only, at a whole scale. Its macOS build needs the Metal Toolchain, which a fresh Xcode does not include, or a runtime shader feature.

This audit narrowed two claims: egui's log rate is one run, and GPUI's log was never tested headless. Neither changes the pick. The egui evidence is unchanged. GPUI has less evidence than the page first said.

Using GPUI would mean one of: pinning a hand-picked set of old crates to keep 0.2.2 building on Linux, a third party's weekly snapshot `gpui-pre`, or a git revision of Zed, which cannot be built on a contributor machine under this project's rules and would be pinned by hash.

## What stays unknown

- GPUI log in a headless test: not tested. No GPUI test scrolls the log or presses Jump to end.
- GPUI on Ubuntu: not built, so its build time, size, headless test and system packages are not known there.
- `gpui-pre` 0.3.14, the weekly snapshot: not tried. It may build on Linux and may have different numbers.
- Frame rates on Ubuntu and Windows: not run, because hosted runners have no display. Neither toolkit's window ran in CI.
- Image snapshots: not tried. The headless tests check state only. The egui log test, which runs in CI on the three systems, checks that setting the scroll position changes the visible rows and that "Jump to end" shows the last line. It does not prove that the rows look right on screen.
- GPUI at a fractional display scale such as 125 %: not run. Reading the code shows the screen would blur.
- Zooming and clicking under load: the canvas rate was measured with pixel edits only. The headless test checks one zoom click.
- A clean, unthrottled 10 second run of GPUI's screen tab on this Mac.
- The minimal Ubuntu package set for egui. The three packages installed are enough. Fewer may do.
