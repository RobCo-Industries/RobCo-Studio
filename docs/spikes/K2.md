# Spike K2: Culvert bytes across systems and build paths

## The question

Does the xPack `arm-none-eabi-gcc` 15.2.1 build Culvert to the same bytes on Ubuntu, macOS and Windows? Are they the same bytes as the Makefile build?

## The method

- `spikes/k2/build.py` builds Culvert by direct commands, with no Make. It copies the flags, input order, link line and seal of Pip-OS `sdk/pipos-app.mk`. It prints the SHA-256 of each object, `libpip.a`, the ELF and `CULVERT.HTP`.
- Two optional cures: `--prefix-map` adds `-ffile-prefix-map=<cwd>=.`, and `--ar-d` builds the archive with `ar rcsD`.
- Inputs: Deitrix `1af21f18`, Pip-OS `5f891e75`, RobCo-Core `79cbd82d`. Compiler: xPack `15.2.1-1.1`, with its archive SHA-256 checked.
- `.github/workflows/spike-k2.yml` runs on the three systems. It runs a raw build on the runner's default checkout and a cured build on a checkout with `core.autocrlf` off. On Ubuntu it also runs `make` and builds with Ubuntu's own `gcc-arm-none-eabi`. The last job, `spikes/k2/compare.py`, fails if any cured file or any xPack `.HTP` differs, or if make and the direct build differ in the ELF or the `.HTP`.

## Result on this Mac

Measured on this Mac, arm64, with the xPack darwin-arm64 archive.

| Comparison | Objects | `libpip.a` | ELF | `.HTP` |
|---|---|---|---|---|
| Make against direct, same source path | equal | differs | equal | equal |
| Direct, two source paths, no cure | differ | differs | differs | equal |
| Direct, two source paths, `--prefix-map --ar-d` | equal | equal | equal | equal |

`CULVERT.HTP` is 14832 bytes with SHA-256 `c05e0c7e8ec20ff84faa2face94ae77aa454f4858e13ab80b577d4d645ab99c0` in every build on this Mac.

Causes found:

- `-g` writes the absolute build directory into `DW_AT_comp_dir`. So objects and the ELF depend on where the source sits. `objcopy -O binary` drops debug sections, so the `.HTP` does not.
- xPack's `ar` 2.45.1 is not deterministic by default. `ar rcs` stores dates, user and group ids. The linker ignores them, so the ELF is the same.
- The ELF has no build ID note. Link order is fixed: `pipos-app.mk` sorts the `sdk/lib` wildcard and lists the rest explicitly.

## What it means for Studio

The sealed tape is what ships, and on this Mac it is the same through both build paths with no cure. To make every intermediate file equal too, Studio must:

1. Compile with the same flags as `pipos-app.mk`, in the same order, with paths relative to the project directory.
2. Add `-ffile-prefix-map=<project dir>=.` to every compile, or drop `-g`. Without it, objects and the ELF carry the build path.
3. Build `libpip.a` with `ar rcsD`, or ship a prebuilt `libpip.a` in the SDK. The SDK's own `ar rcs` is not deterministic with xPack binutils.
4. Keep the link order of `pipos-app.mk`: `crt0`, sources in `SRCS` order, `libpip.a`, `-lgcc`.
5. Read sources as committed bytes. Do not let a Windows checkout turn LF into CRLF. Whether CRLF changes any byte is still to be shown by CI.

For `flags.json`, rule 2 means it needs a placeholder for the project directory, or the prefix map must be added by Studio.

## What stays unknown

- Whether Ubuntu and Windows give the same bytes as macOS. This needs the CI run.
- Whether a CRLF checkout on Windows changes the objects or the `.HTP`.
- Whether make with xPack on Ubuntu matches the direct build there. On this Mac it does.
- How far Ubuntu's own compiler is from xPack.
