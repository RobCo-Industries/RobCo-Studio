# Spike K2: Culvert bytes across systems and build paths

## The question

Does the xPack `arm-none-eabi-gcc` 15.2.1 build Culvert to the same bytes on Ubuntu, macOS and Windows? Are they the same bytes as the Makefile build?

## The method

- `spikes/k2/build.py` builds Culvert by direct commands, with no Make. It copies the flags, input order, link line and seal of Pip-OS `sdk/pipos-app.mk`. It prints the SHA-256 of each object, `libpip.a`, the ELF and `CULVERT.HTP`.
- Optional cures: `--prefix-map` maps the project and toolchain directories with `-ffile-prefix-map`, `--no-ident` adds `-fno-ident`, `--ar-d` builds the archive with `ar rcsD`, and `--strip-elf` also writes the ELF without debug info.
- Inputs: Deitrix `1af21f18`, Pip-OS `5f891e75`, RobCo-Core `79cbd82d`. Compiler: xPack `15.2.1-1.1`, with its archive SHA-256 checked.
- `.github/workflows/spike-k2.yml` runs on the three systems. It runs a raw build on the runner's default checkout and a cured build on a checkout with `core.autocrlf` off. On Ubuntu it also runs `make` and builds with Ubuntu's own `gcc-arm-none-eabi`. The last job, `spikes/k2/compare.py`, fails if any cured file but the full ELF differs, if any xPack `.HTP` differs,, or if make and the direct build differ in the ELF or the `.HTP`.

## Result on this Mac

Measured on this Mac, arm64, with the xPack darwin-arm64 archive.

| Comparison | Objects | `libpip.a` | ELF | `.HTP` |
|---|---|---|---|---|
| Make against direct, same source path | equal | differs | equal | equal |
| Direct, two source paths, no cure | differ | differs | differs | equal |
| Direct, two source paths, `--prefix-map --ar-d`, project map only | equal | equal | equal | equal |

`CULVERT.HTP` is 14832 bytes with SHA-256 `c05e0c7e8ec20ff84faa2face94ae77aa454f4858e13ab80b577d4d645ab99c0` in every build on this Mac.

Causes found:

- `-g` writes the absolute build directory into `DW_AT_comp_dir`. So objects and the ELF depend on where the source sits. `objcopy -O binary` drops debug sections, so the `.HTP` does not.
- xPack's `ar` 2.45.1 is not deterministic by default. `ar rcs` stores dates, user and group ids. The linker ignores them, so the ELF is the same.
- The ELF has no build ID note. Link order is fixed: `pipos-app.mk` sorts the `sdk/lib` wildcard and lists the rest explicitly.

## Result on CI

Run: [45652169777](https://github.com/RobCo-Industries/RobCo-Studio/actions/runs/45652169777). Runners: `ubuntu-latest` x64, `macos-latest` arm64, `windows-latest` x64, each with its xPack `15.2.1-1.1` archive.

| System | Raw `.HTP` | Cured objects and `libpip.a` | Cured ELF without debug info | Cured full ELF |
|---|---|---|---|---|
| Ubuntu | `c05e0c7e…`, equal | equal | `63651776…`, equal | `f673dc2d…` |
| macOS | `c05e0c7e…`, equal | equal | `63651776…`, equal | `f673dc2d…` |
| Windows | `c05e0c7e…`, equal | equal | `63651776…`, equal | differs |

"Raw" uses the Makefile's flags on the runner's default checkout. "Cured" uses all four cures and a checkout with `core.autocrlf` off. The `.HTP` hash is the one measured on this Mac.

Make against direct, on Ubuntu with xPack, in the same checkout: every object, the ELF and the `.HTP` are equal. Only `libpip.a` differs, through the dates that `ar rcs` stores.

CRLF on Windows: the runner sets `core.autocrlf=true` in its system git config, so the raw build compiled CRLF sources. Its `.HTP` is still equal to the others. Its objects differ, but the raw objects of every system differ through paths, so this run does not isolate a CRLF effect on objects.

Ubuntu's `gcc-arm-none-eabi` 14.2.1 against xPack 15.2.1: the `.HTP` differs, `08e3ec08…`, as expected from another compiler version.

Causes found on CI, beyond those found on this Mac:

- The xPack include directory, `<toolchain>/lib/gcc/arm-none-eabi/15.2.1/include`, lands in the debug info. A second `-ffile-prefix-map` for the toolchain root cures it.
- Each object's `.comment` names the host: `xPack GNU Arm Embedded GCC arm64` on macOS and `x86_64` on the others. `-fno-ident` cures it. `holotape.ld` discards `.comment`, so the ELF never saw it.
- The Windows archive's `libgcc.a` carries debug info for `lib1funcs.S`, with the publisher's build paths. The Linux and macOS archives do not. So the Windows full ELF differs in its debug sections only. No compile flag cures this. With debug info stripped, the three ELFs are equal.

Earlier rounds: [45651400867](https://github.com/RobCo-Industries/RobCo-Studio/actions/runs/45651400867) showed the toolchain path and the ident string. [45651908792](https://github.com/RobCo-Industries/RobCo-Studio/actions/runs/45651908792) kept the outputs that showed the `libgcc.a` debug info.

## What it means for Studio

The sealed tape is equal on the three systems and through both build paths, with the Makefile's flags unchanged. The `.HTP` needs no cure. To make the intermediate files equal too, Studio must:

1. Compile with the flags of `pipos-app.mk`, in its order, in the project directory, with relative source paths.
2. Keep the link order: `crt0`, sources in `SRCS` order, `libpip.a`, `-lgcc`.
3. Add `-ffile-prefix-map=<project dir>=.` and `-ffile-prefix-map=<toolchain root>=<fixed name>` to every compile, with both slash spellings on Windows.
4. Add `-fno-ident`, or compare objects without `.comment`.
5. Build `libpip.a` with `ar rcsD`, or ship a prebuilt one in the SDK.
6. Compare ELFs without debug info, or accept that the Windows ELF differs in its debug sections through xPack's `libgcc.a`.
7. Read sources as committed bytes. This keeps CRLF out, though the `.HTP` did not change with it.

## Open points for the owner

- Path maps and `flags.json`: (a) `flags.json` carries placeholders for the project and toolchain directories, (b) Studio adds the maps itself, or (c) tape builds drop `-g`.
- `-fno-ident`: (a) `pipos-app.mk` adds it, (b) Studio adds it, or (c) only the ELF and the `.HTP` are compared.
- `libpip.a`: (a) Pip-OS moves to `ar rcsD`, (b) the SDK ships a prebuilt archive, or (c) only the ELF and the `.HTP` must be equal.
- The ELF test: (a) compare without debug info, or (b) compare only the `.HTP`.

## What stays unknown

- Whether CRLF sources change any object. The `.HTP` did not change.
- The SDK's sample tape. This spike built only Culvert.
- Windows on arm64 and macOS on x64: not run. The runners used are x64 Windows and arm64 macOS.
