# Spike K5: frame rate of QMP screendump

## The question

Studio's simulator shows QEMU's screen by calling the QMP command `screendump` again and again. It is the call the suite's golden-image tests use. Studio wants 15 to 30 frames a second. The plan's fallback is QEMU's VNC server on loopback.

How many frames a second does `screendump` give, at what cost, and is it enough?

## Short answer

Yes. On this Mac under load and on a hosted Linux runner, `screendump` in PPM gives 145 to 260 frames a second at 640 by 480 when polled flat out, on `raspi0`, `raspi2b` and `raspi3b`. At a fixed 30 frames a second each frame takes about 4 to 7 ms from request to decoded pixels. The cost is in the guest: each call stops the guest for those milliseconds, so at 30 frames a second the guest runs about 10 % slower, and flat out it runs at a quarter of its speed.

## Method

- `spikes/k5/guest/` is a bare-metal guest built on RobCo-Core's library, out of tree, in `spikes/k5/.cache/`. It sets up the framebuffer and then, in a loop, moves a 32 by 32 square and draws its frame counter as a row of 32 cells. So every frame differs from the one before. Every 250 ms of guest time it prints `@RC stage=k5 ev=rate it=<frames drawn> ms=<guest ms>` on serial. Frames drawn per host second is the guest's speed.
- It is built twice: 640 by 480, the size every chain in the suite uses in QEMU, and 320 by 240. Pip-OS, UOS and RobCo-Core's chain tests all call `fb_init(640, 480, 32)`. The Pip-Boy's 320 by 240 surface is scaled by 2 into that framebuffer, so the Pip-Boy chain's `screendump` is also 640 by 480. The 320 by 240 runs show what a smaller framebuffer would cost.
- `spikes/k5/src/` is the poller, in Rust. It starts QEMU itself with the same boot as the suite's harness (`tests/harness/boot.py`: firmware stub, loader devices, parameter block, the AArch64 shim on `raspi3b`), but with QMP and serial on TCP loopback as the plan says. It opens two QMP connections. A watchdog kills QEMU after 20 s, and a guard kills it on any exit.
- The harness calls `screendump` with a file name only, so QEMU writes PPM to a file, and the test reads it back. The poller does the same. Each frame is read and decoded to RGBA in memory, as a window would upload it, and hashed.
- One QEMU run has these phases, 2 s each:
  - `idle`: no polling; a key every 50 ms on the second connection.
  - `ppm-15`, `ppm-30`: PPM to a file at a fixed 15 and 30 frames a second.
  - `ppm-max`: PPM to a file as fast as possible.
  - `png-max`: PNG to a file as fast as possible, decoded with the `png` crate.
  - `ppm-fifo-max`: PPM into a named pipe the poller reads, so no file is written.
  - `ppm-max-keys-same`, `ppm-max-keys-second`: PPM flat out, plus a QMP `send-key` every 50 ms, on the same connection or on the second one.
- Each phase records frames a second, the time from request to QMP reply, the read and decode time, the total from request to decoded pixels as median, 95th centile and worst, CPU of QEMU and of the poller, and the guest's speed. CPU comes from `ps` on macOS and `/proc` on Linux. 100 % is one core.
- Distinct frames: the poller counts how often a frame's hash differs from the one before, and the unique hashes. A phase where every frame is the same fails with `FAIL: ... every frame was the same ... the benchmark measured a still picture`. In every run on record, every frame differed from the one before.
- VNC: the same QEMU started with `-vnc 127.0.0.1:N`, and a minimal RFB 3.8 client of about 150 lines in `src/lib.rs`: no security, 32-bit colour, Raw encoding only. It asks for incremental updates at 30 a second, then as fast as the server answers, applies each update to its own copy of the screen, and counts updates and distinct frames.
- One command runs all of it: `spikes/k5/bench.sh <RobCo-Core checkout> [result file]`. It needs `arm-none-eabi-gcc`, `make`, `cargo` and QEMU on the PATH. `K5_BOARDS`, `K5_SIZES`, `K5_MODES` and `K5_TMP` narrow it. It prints no path, user or machine name.
- CI: [`spike-k5.yml`](../../.github/workflows/spike-k5.yml) builds the poller on Ubuntu, macOS and Windows, checks format and Clippy, and runs the unit tests. Then it runs the benchmark on Linux in the suite's container `robco-ci:ba6372158e4b` with RobCo-Core at `73a6cb2a67b3`, twice: files on the container's disk, then files in `/dev/shm`.

Of the 4.3 ms on the Mac, about 3.9 ms is QEMU's own work until it replies, and 0.4 ms is reading the 921,615 byte file and decoding it in Rust (`reply` and `read_decode` in the raw files). At 320 by 240 the total is about 2.1 to 2.8 ms.

The first CI run, [45692127472](https://github.com/RobCo-Industries/RobCo-Studio/actions/runs/45692127472), wrote to the same kind of disk and saw stalls: flat out at 640 by 480, the 95th centile was 16 to 78 ms and the worst 100 to 240 ms, and at 30 frames a second the worst was 34 to 113 ms. The second run did not. With `/dev/shm`, and with the named pipe, no run had a stall above 14 ms.

### Cost at 15 and 30 frames a second, 640 by 480

CPU: 100 % is one core. Guest speed is the guest's draws a second against its own idle phase in the same run.

| Board | Where | Rate held | QEMU CPU, idle, 15, 30 | Poller CPU at 15, 30 | Guest speed at 15, 30, flat out |
|---|---|---|---|---|---|
| `raspi0` | Mac | 15.4, 30.4 | 101, 101, 101 % | 1, 2 % | -3 %, -9 %, -72 % |
| `raspi2b` | Mac | 15.4, 30.4 | 100, 101, 102 % | 1, 2 % | -4 %, -11 %, -72 % |
| `raspi3b` | Mac | 15.4, 30.4 | 100, 101, 100 % | 1, 2 % | -3 %, -11 %, -72 % |
| `raspi0` | CI disk | 30.4 at 30 | 101, n/a, 103 % | 4 % at 30 | -11 % at 30, -67 % flat out |
| `raspi2b` | CI disk | 30.4 at 30 | 101, n/a, 103 % | 5 % at 30 | -10 % at 30, -66 % flat out |
| `raspi3b` | CI disk | 30.4 at 30 | 101, n/a, 102 % | 5 % at 30 | -16 % at 30, -69 % flat out |

The CI disk pass has a 15 frames a second phase too; see the raw file. QEMU uses one core whether polled or not: the guest spins on one emulated CPU. `screendump` takes its time from that core. Each call holds QEMU's main lock for about 4 ms, and the guest's CPU waits. 30 calls of 4 ms is 12 % of each second, which matches the slowdown at 30. This is our reading of the numbers, not a QEMU trace. The guest's clock stayed at 1.00 guest seconds per host second in every phase: the guest runs fewer instructions, its timer does not slow.

### PNG

| Where | 640 by 480 flat out | 320 by 240 flat out |
|---|---|---|
| Mac | 98.9 to 102.8 frames a second, 9.4 to 9.8 ms median, guest at 13 % to 14 % of idle speed | 301.6 to 322.5, 3.0 to 3.1 ms |
| CI | Not run: the suite's QEMU is built without libpng and answers `Enable PNG support with libpng for screendump` | Not run, same reason |

PNG takes twice as long as PPM in QEMU, so it stops the guest twice as long per frame. The files were about 1.1 KB, because the test screen is mostly black. A real screen compresses less, and QEMU's encoding time for it was not measured. PNG saves only file size, which a loopback poller does not need.

### Where the file goes, and avoiding the disk

The suite's harness gives QEMU a path in a temporary folder, and QEMU writes a 921,615 byte PPM there, which the test reads back. On this Mac the poller used `spikes/k5/.cache/tmp/` on the internal SSD; on CI, `/tmp` on the container's disk, then `/dev/shm`, which is memory.

| Sink, 640 by 480 flat out | Mac | CI |
|---|---|---|
| File on disk | 212 frames a second, 4.3 ms median, poller 16 % | 187 to 209, 4.1 to 4.4 ms median, poller 23 to 24 %; one of two runs had stalls up to 300 ms |
| File in `/dev/shm` | Not run: macOS has no `/dev/shm` | 252 to 260, 3.2 to 3.4 ms median, poller 27 to 28 % |
| Named pipe | 235 to 251, 3.6 to 3.8 ms median, poller 34 to 37 % | 235 to 249, 3.2 to 3.4 ms median, poller 47 to 49 % |

A named pipe avoids the disk on macOS and Linux and gains about 0.7 ms a frame. QEMU opens it as a file and blocks until the poller opens the other end, so the poller must open it right after sending the command. The poller's CPU goes up, because it reads the frame in pipe-sized pieces. Windows has no named pipe that QEMU opens as a file path, so it was not tried there. QMP can also take a file descriptor with `getfd` or `add-fd`, but only over a Unix socket, which Windows lacks and the plan's TCP QMP cannot carry. That was not tried.

### Keys while polling

QMP `send-key` every 50 ms, with `screendump` flat out at 640 by 480. Latency in ms, median, 95th centile, worst. The board has no keyboard device, so the key goes nowhere, but QEMU answered every one without error. The suite's guests read keys from the serial script channel or GPIO, not from QMP. `send-key` stands in for any small QMP command.

| Where | Not polling, second connection | Same connection | Second connection |
|---|---|---|---|
| Mac, `raspi0` | 0.45, 0.52, 0.62 | 3.29, 5.87, 13.36 | 2.10, 3.36, 3.74 |
| Mac, `raspi2b` | 0.44, 0.48, 0.49 | 2.43, 4.80, 6.23 | 2.12, 3.51, 4.18 |
| Mac, `raspi3b` | 0.45, 0.54, 2.40 | 2.39, 4.80, 5.54 | 0.80, 2.82, 4.02 |
| CI disk, `raspi0` | 0.64, 0.68, 0.70 | 3.14, 6.27, 6.37 | 1.00, 3.13, 3.89 |
| CI disk, `raspi2b` | 0.72, 0.79, 0.83 | 3.69, 5.24, 5.53 | 1.00, 3.66, 6.31 |
| CI disk, `raspi3b` | 0.67, 0.75, 0.78 | 2.84, 5.33, 5.45 | 1.38, 3.36, 3.62 |

On the same connection a key waits for the frame in flight. On a second connection it still waits for QEMU's main loop, which runs one command at a time, but less. Either way a key lands in under 14 ms in these runs, against a 33 ms frame at 30 a second. The first CI run, during its disk stalls, had worst cases of 10 to 372 ms on both kinds of connection. Adding keys cost the flat-out frame rate up to 14 % on CI and 2 % on the Mac.

VNC stops at about 29 updates a second whatever the client asks. QEMU's display refresh timer sets that pace; the default interval in QEMU's source is 30 ms. Each update carries only the changed rectangles, about 730 KB a second here. VNC did not slow the guest. Every update differed from the one before. The client keeps its own copy of the screen, built from rectangles, so it is not the image the golden tests compare.

## What it means for Studio

- `screendump` is enough. 30 frames a second is reached with room to spare, about 6 to 7 times over at 640 by 480, on all three boards, on a loaded Mac and on a hosted runner. The question was "below 30 under load?" and the answer is no.
- The cost to watch is the guest, not the host. Each frame stops the guest for about 4 ms. At 30 a second the guest loses about 10 %, at 15 about 3 to 4 %. Polling as fast as possible would cut the guest to a quarter. Studio must pace its polls and never poll flat out.
- PPM, not PNG. PNG costs QEMU twice the time per frame, and the suite's own QEMU build has no PNG at all. The harness already uses PPM.
- VNC as the fallback is not needed for speed. It costs the guest nothing, but it tops out at 29 updates a second, adds about 35 ms of delay, shows a reconstruction rather than the tested image, and the suite's QEMU build lacks it. If Studio ships its own QEMU, as D15 says, VNC is a build option, not a given.

Options the plan leaves open, not picked here:

- Rate to offer: 15 frames a second costs the guest about 3 to 4 %; 30 costs about 10 %. Options: fixed 30; fixed 15; a user setting; or a rate that adapts, slowing when the guest's markers show it slowed.
- Where QEMU writes the frame: a file in the system's temporary folder, as the harness does; a named pipe on macOS and Linux with a file on Windows; or memory-backed storage where there is some, `/dev/shm` on Linux. The disk file had stalls up to 300 ms in one of two CI runs.
- One QMP connection or two: one is enough for keys, with a key late by a 95th centile of up to about 6 ms. A second connection cuts the median to about 1 to 2 ms and keeps the poller and the input path apart in code. Two connections cost one more `-qmp` argument.
- Change detection: QEMU returns a full frame every time. Studio can hash it, as the poller does, and skip the texture upload when nothing changed. That is a choice for milestone S2.

What would change the answer:

- A guest that needs all of its emulated CPU, such as a game near its frame budget, would feel the 10 % at 30 frames a second.
- A larger framebuffer. Cost grows with pixels: 320 by 240 costs about half of 640 by 480.
- Studio's own QEMU build, from spike K1, on macOS and Windows. Its `screendump` speed was not measured.
- A disk that stalls, on a user's machine, if Studio writes frames to a file.

## What stays unknown

- Rates on a calm machine: every Mac number was taken with load averages of 4 to 7. They are lower bounds. Run `spikes/k5/bench.sh <RobCo-Core checkout> spikes/k5/results/mac-calm.txt` again when the machine is calm.
- macOS and Windows runners, with spike K1's QEMU builds: not run. It would need K1's build steps in this job, which is not cheap. The poller builds and tests on both.
- PNG and VNC on Linux: not run, because the suite's QEMU build has neither.
- PNG cost on a full, busy screen: not run. The test screen compresses to about 1 KB.
- Passing a file descriptor to QEMU with `getfd` or `add-fd`: not tried. It needs a Unix-socket QMP.
- Real key input under polling: the guest did not read keys. `send-key` measured QMP latency only.
- Why the first CI run's disk stalled and the second did not: not known. Two runs are not enough to say how often it happens.
- Each phase lasted 2 s to keep each QEMU under 20 s. Longer phases would give steadier numbers.
